## Problem Statement & Motivation

Environmental planning typically compares a handful of predefined adaptation strategies chosen by intuition. Real decision-making is harder than that: futures are uncertain, budgets are limited, objectives conflict with each other (cheaper vs. more resilient vs. faster recovery), and infrastructure, population, and climate interact in ways that are difficult to reason about by hand.

ClimateShield explores this properly: instead of comparing a few hand-picked strategies, it generates and simulates **every feasible combination** of available interventions, runs each one through **seeded Monte Carlo uncertainty analysis**, and ranks them with a **transparent, weighted decision score** — grounded in what the simulation actually produced, not just declared intervention effects.

This is a prototype decision-support tool using synthetic, clearly-labeled modelled parameters. It does not predict real-world climate outcomes.

## Solution Overview

A city planner provides a budget, a climate scenario, and objective priorities (cost vs. flood protection vs. heat protection vs. population protection vs. recovery speed). ClimateShield:

1. Builds a baseline (no-intervention) risk profile for the scenario.
2. Generates every non-empty combination of configured interventions and filters out anything over budget.
3. Runs a seeded Monte Carlo simulation for every feasible combination, under the identical random draws (common random numbers), for a fair comparison.
4. Scores and ranks every combination with a transparent multi-objective formula.
5. Recommends the top strategy, with a plain-language, data-driven reason — generated deterministically, no AI required.
6. Validates the recommendation against the no-intervention baseline, side by side.
7. Offers one-variable-at-a-time sensitivity analysis to show which modelling assumptions matter most.

## Key Features

- 5 climate scenarios, 6 adaptation interventions — all configuration-driven, expandable without touching engine code
- Deterministic core simulation engine with a seeded PRNG (never `Math.random()`)
- Monte Carlo uncertainty quantification (100 / 500 / 1000 runs, server-capped at 2000)
- Exhaustive strategy generation via power set (63 combinations from 6 interventions today)
- Transparent multi-objective decision scoring, blending declared intervention effects with simulated outcomes
- Baseline vs. recommended strategy validation, built into the recommendation response
- One-variable-at-a-time sensitivity analysis (rainfall intensity, temperature, intervention effectiveness, infrastructure vulnerability)
- Full reproducibility: same seed + same inputs always produces the identical result, verifiable via "Re-run"
- MongoDB-backed experiment history with view/re-run, degrading gracefully when persistence is unavailable
- Strict objective-weight validation (rejects negative/NaN/Infinity/all-zero, with a documented default for omitted weights)
- Dark climate-tech command-center frontend, wired to the real backend with no duplicated simulation logic

## System Architecture

```
React (Vite, TypeScript, Tailwind)
        ↓
Express REST API (TypeScript)
        ↓
Simulation / Recommendation Engine
        ├── Scenario Engine        (scenario config → hazard profile)
        ├── Intervention Engine    (selected interventions → strategy effect + budget check)
        ├── Risk Model             (single stochastic run: risk, damage, population, recovery)
        ├── Monte Carlo            (N seeded runs → uncertainty statistics)
        ├── Strategy Generator     (power set of configured interventions)
        ├── Decision Scoring       (multi-objective ranking formula)
        └── Sensitivity Analysis   (one-variable-at-a-time perturbation sweep)
        ↓
MongoDB (experiment history — optional, app works fully without it)
```

Gemini is **not implemented** in this submission. The architecture reserves a place for it (`Simulation Result → Gemini → human-readable explanation`, strictly outside the computation path, never `React → Gemini → result`), but the deterministic reason string already generated by the recommendation engine was judged sufficient for this submission, and no code path depends on `GEMINI_API_KEY` being present. If added later, it would only ever summarize an already-computed result — never compute one.

## Core Technical Mechanism

- **Scenario modelling**: each scenario (`baseline`, `heavy-rainfall`, `extreme-flood`, `heatwave`, `compound-extreme`) is a config record — temperature increase, rainfall intensity multiplier, flood probability, heatwave probability — converted into a `HazardProfile` (flood/heat hazard, 0–1).
- **Intervention modelling**: each intervention (`drainage-upgrade`, `flood-barrier`, `green-roofs`, `urban-forest`, `cool-roofs`, `heat-shelters`) declares cost and fractional mitigation effects. Selecting a combination sums these effects (deduplicated, so a repeated id is never double-counted) and caps the total at 90% per hazard (diminishing returns).
- **Risk calculation**: one stochastic Monte Carlo draw applies city-level mitigation (drainage capacity, green coverage), the strategy's mitigation, and ±10% Gaussian jitter, to compute flood risk, heat risk, expected damage (₹ Cr), population affected, and recovery time.
- **Strategy generation**: the power set of currently configured intervention ids, filtered to those within budget.
- **Monte Carlo simulation**: the risk model is run N times per strategy (same seed across every strategy compared, for fairness) and aggregated into mean/median/min/max/standard deviation/success probability.
- **Seeded randomness**: a single deterministic PRNG (`mulberry32`) drives every random draw in the engine; a Box-Muller transform derives Gaussian variation from it. No other randomness source exists in the simulation or API code.
- **Multi-objective decision scoring**: strategies are ranked by a formula blending declared effects and simulated outcomes, weighted by user-adjustable priorities (see below).
- **Recommendation**: the top-ranked feasible strategy, with alternatives and a generated, data-driven explanation.
- **Sensitivity analysis**: holding a strategy fixed, each of four parameters is swept -10%→+10% in 5 steps and the resulting swing in expected damage is measured and ranked.

## Mathematical Model

All formulas below are taken directly from the implementation (`backend/src/simulation/`), not idealized or invented for this document.

**Hazard profile** (`scenarioEngine.ts`):
```
floodHazard = clamp01(floodProbability × rainfallIntensityMultiplier)
heatHazard  = clamp01(heatwaveProbability + temperatureIncreaseC × 0.05)
```

**Strategy effect** (`interventionEngine.ts`) — sum of selected interventions' declared effects, deduplicated, each capped at 0.9:
```
floodReduction, heatReduction, infrastructureProtection,
populationProtection, recoveryImprovement = min(Σ effects, 0.9)
```

**Single Monte Carlo run** (`riskModel.ts`):
```
floodJitter = 1 + Gaussian(0, 0.10)
heatJitter  = 1 + Gaussian(0, 0.10)

effectiveFloodHazard = floodHazard × (1 − drainageCapacity × 0.3)
effectiveHeatHazard  = heatHazard  × (1 − greenCoverage × 0.2)

floodRisk = clamp01(effectiveFloodHazard × (1 − floodReduction) × floodJitter)
heatRisk  = clamp01(effectiveHeatHazard  × (1 − heatReduction)  × heatJitter)

damageScale = (population / 1,000,000) × 40   // ₹ Cr, at full unmitigated risk
baseDamagePotential = (floodRisk × 0.6 + heatRisk × 0.4) × infrastructureVulnerability × damageScale
damageCr = max(0, baseDamagePotential × (1 − infrastructureProtection))

populationAffected = clamp(population × (floodRisk × 0.5 + heatRisk × 0.3) × (1 − populationProtection), 0, population)

recoveryMonths = max(1, (6 + (floodRisk + heatRisk) × 24) × (1 − recoveryImprovement))
```

**Resilience score** (declared-effects only, `scoring.ts`):
```
resilienceScore = w_flood·floodReduction + w_heat·heatReduction
                 + w_pop·populationProtection + w_recovery·recoveryImprovement
                 − w_cost·min(totalCost / budget, 1)
```

**Decision score** (used for ranking — blends declared effects with simulated outcomes vs. the baseline):
```
componentX = clamp01(0.5 × designFractionX + 0.5 × outcomeFractionX)
outcomeFractionX = clamp01(1 − strategyValueX / baselineValueX)

decisionScore = w_flood·floodComponent + w_heat·heatComponent
              + w_pop·populationComponent + w_recovery·recoveryComponent
              − w_cost·min(totalCost / budget, 1)
```

All 5 weights (`cost`, `floodProtection`, `heatProtection`, `populationProtection`, `recovery`) are validated and auto-normalized to sum to 1.

## Uncertainty Model

- **Seeded PRNG**: `mulberry32(seed)` — a small, fast, well-known deterministic 32-bit generator. Not cryptographically secure; not needed for a simulation engine.
- **Monte Carlo**: the risk model above is run N times (100 / 500 / 1000, server-clamped to [10, 2000]) per strategy, consuming the seeded generator only.
- **Gaussian variation**: derived from the uniform PRNG via a Box-Muller transform, applied as ±10% relative jitter on flood and heat risk per run.
- **Aggregation**: across all N runs' expected damage, the engine computes mean, median, min, max, and standard deviation.
- **Success probability**: the fraction of runs where both flood risk and heat risk stayed under a 0.5 mid-risk threshold.

## Strategy Generation

The strategy generator computes the power set (all non-empty subsets) of the currently configured intervention ids, using a bitmask over indices — it has no knowledge of what any intervention *is*, only that there are N of them.

| Interventions configured | Combinations generated |
|---|---|
| 4 | 15 |
| 6 (current) | 63 |

Adding a 7th intervention to `data/interventions.ts` would make it 127 combinations automatically, with zero engine code changes. A safety guard rejects exhaustive generation above 20 interventions (over a million combinations), recommending a sampling-based approach instead — not yet needed, not yet built.

## Decision Scoring

The decision score is a **prototype modelling choice**, not a scientifically validated formula. Specifically:

- The 50/50 blend between "declared intervention effect" and "simulated outcome relative to baseline" is a judgment call made by the development team to ground rankings partly in real Monte Carlo results rather than declared effects alone. **It is not claimed to be optimal, calibrated, or scientifically derived.**
- Objective weights are user-adjustable and auto-normalized; the ranking is fully transparent and reproducible for a given weight set, but "correct" weighting is inherently a policy choice, not a computable fact.
- Maintenance cost (`totalMaintenanceCostCr`) is calculated and surfaced for every strategy but is **deliberately excluded** from the budget feasibility check and from the decision score — documented as informational-only for this prototype (see Assumptions).

## Validation / Experiments

All results below were generated live against the running implementation immediately before this submission, using the default synthetic city profile (Nagpur-like, population 2.5M) and objective weights `{cost: 0.2, flood: 0.3, heat: 0.2, population: 0.2, recovery: 0.1}` unless noted.

**Reproducibility experiment** — identical request (`extreme-flood`, ₹100 Cr, seed 2026, 500 runs) sent twice: responses were byte-for-byte identical, including every Monte Carlo statistic.

**Baseline vs. recommended strategy** — `extreme-flood`, ₹100 Cr, seed 2026: baseline (no intervention) expected damage ₹32.16 Cr; recommended strategy (Flood Barrier + Urban Forest + Heat Shelters, ₹100 Cr) expected damage ₹9.48 Cr — a 71% reduction, with 39 of 63 generated combinations feasible under budget.

**Strategy comparison** — the same run ranks 5 strategies for display, each with cost, damage, flood/heat risk, population impact, recovery time, success probability, and decision score, computed under identical seeded conditions for a fair comparison.

**Budget-change experiment** — dropping the same scenario from ₹100 Cr to ₹60 Cr changed the recommendation from *Flood Barrier + Urban Forest + Heat Shelters* to *Green Roofs + Urban Forest + Heat Shelters*, and the feasible-strategy count from 39 to 18 — confirming the recommendation is recalculated, not hardcoded.

**Objective-weight sensitivity** — under `extreme-flood`, a flood-dominant weight profile (`floodProtection=1`, all else 0) recommends *Drainage Upgrade + Flood Barrier*; a heat-dominant profile (`heatProtection=1`, all else 0) recommends *Green Roofs + Urban Forest + Cool Roofs + Heat Shelters* — the ranking genuinely changes with priorities.

**Scenario change** — switching the same budget/seed from `extreme-flood` to `heatwave` changes both the recommendation (to *Drainage Upgrade + Green Roofs + Urban Forest + Heat Shelters*) and the underlying risk balance (heatwave baseline: 65% heat risk vs. 6% flood risk — inverted from the flood scenario, as expected).

**Sensitivity analysis** — under `heavy-rainfall` (chosen deliberately; see Limitations) with Drainage Upgrade selected: infrastructure vulnerability accounts for 41.9% of the observed damage swing, rainfall intensity 34.3%, intervention effectiveness 22.1%, temperature increase 1.8%.

## Assumptions

Every numeric constant below is a **prototype simulation assumption**, not a scientific measurement:

- Scenario and intervention parameters (temperature deltas, rainfall multipliers, cost figures, mitigation fractions) are synthetic, illustrative values chosen to produce a defensible demo — not sourced from real climate data.
- Stacking multiple interventions' effects is capped at 90% mitigation per hazard (diminishing returns), to avoid an unrealistic full elimination of risk.
- Per-run uncertainty is modelled as ±10% Gaussian jitter on flood and heat risk — a simplification, not a calibrated uncertainty model.
- Damage is scaled at ₹40 Cr per million population at full unmitigated risk — an arbitrary but internally consistent scaling constant.
- "Success" in a Monte Carlo run is defined as both flood and heat risk staying under a 0.5 threshold — a simple, transparent, but arbitrary cutoff.
- The decision score's 50/50 design/outcome blend is a prototype modelling choice (see Decision Scoring above), not claimed to be optimal.
- Maintenance cost is computed and displayed but deliberately **not** part of budget feasibility or the decision score in this submission.
- The city profile (population, drainage capacity, green coverage, infrastructure vulnerability) is a single synthetic "Nagpur-like" default, not real municipal data.

## Limitations

- This is **not a real-world climate forecasting system**. It does not predict actual future climate outcomes.
- All climate and intervention parameters are synthetic prototype assumptions, clearly labeled as such throughout the codebase and this document.
- The city model is a single flat profile (population, drainage, green coverage, infrastructure vulnerability, hospital capacity) — not a spatial or zoned model.
- No real GIS or mapping is used; there is no spatial representation of *where* risk or interventions apply within the city.
- The sensitivity analysis model can saturate: under `extreme-flood`, flood hazard is already clamped at its ceiling (0.65 × 1.8 = 1.17 → 1.0), so rainfall-intensity sensitivity shows as 0% there specifically — a real, verified property of the current model, not a bug, but worth knowing before choosing a demo scenario for that specific chart (use `heavy-rainfall` instead, as documented above).
- Would require calibration against real climate, infrastructure, and cost data before any claim of real-world decision-support validity.
- Experiment history requires a connected MongoDB instance; without one, simulations still run fully, but no history is retained across restarts.
- Gemini-based natural-language explanation is not implemented in this submission.

## Render deployment

ClimateShield is configured as two Render services from the root `render.yaml`:

- `climateshield-api` — Node/Express backend
- `climateshield-web` — Vite/React static frontend

The frontend receives the backend's Render URL automatically through `VITE_API_BASE_URL`. MongoDB remains external persistence and is supplied as the secret `MONGODB_URI` during Blueprint creation. Gemini is not required by the current implementation.

### Deploy

1. Push the repository to the private GitHub repository.
2. In Render, choose **New → Blueprint** and connect the repository.
3. Render reads the root `render.yaml` and creates both services.
4. When prompted for `MONGODB_URI`, paste the working MongoDB Atlas connection string.
5. Deploy the Blueprint.
6. Verify the backend health URL: `https://<backend>.onrender.com/api/health`.
7. Open the frontend URL and run the same Extreme Flood / ₹100 Cr / 500 runs / seed 2026 demo.

The backend binds to `0.0.0.0` and uses Render's `PORT` automatically. The core simulator does not require MongoDB to calculate recommendations; MongoDB enables experiment persistence/history.
